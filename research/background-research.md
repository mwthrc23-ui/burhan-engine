# بُرهان — تقرير بحث الخلفية والفرصة

> الاسم «بُرهان» اسم عمل مؤقت إلى حين فحص العلامة التجارية والنطاقات.

- التاريخ: 2 أغسطس 2026
- المرحلة: بحث الخلفية قبل نمذجة التدفق والـPRD
- النطاق المقترح: منتج مستقل، وليس جزءًا من مشروع تحدّي

## الملخص التنفيذي

فكرة «نظام تشغيل ذكي للعمل» صحيحة من حيث الحاجة، لكنها بصيغتها الأفقية العامة تدخل مباشرة في منافسة مع منصات ضخمة مثل Atlassian Rovo وGlean وPalantir AIP وCelonis. بناء نسخة عامة أخرى من «وكلاء + تكاملات + محادثة» لن يصنع أفضلية قابلة للدفاع.

الفرصة الأوضح هي منتج أضيق وأقوى:

**مختبر موثّق لحل المشكلات التقنية للفرق الرقمية الصغيرة، يجمع الأدلة، يشغّل حلولًا متنافسة في بيئة آمنة، يتحقق من النتيجة، ثم يحوّل الحل الناجح إلى إجراء قابل للتكرار.**

الميزة المركزية ليست عدد الوكلاء، بل «عقد النتيجة»: لا تُعد المهمة منجزة حتى يثبت النظام حالة ما قبل التنفيذ، والتغيير، واختبار القبول، وحالة ما بعد التنفيذ، وإمكانية التراجع.

## تقييم معقولية الحاجة

الحاجة حقيقية، لكن الثقة هي عنق الزجاجة. أظهر استطلاع Stack Overflow للمطورين لعام 2025 أن:

- 46% لا يثقون بدقة أدوات الذكاء الاصطناعي مقابل 33% يثقون بها.
- 66% يشتكون من حلول «تكاد تكون صحيحة».
- 45% وجدوا أن تصحيح الكود المولّد بالذكاء الاصطناعي يستغرق وقتًا أكبر.
- 87% لديهم مخاوف من الدقة، و81% لديهم مخاوف من أمن وخصوصية البيانات.
- في المقابل، 52% يرون أثرًا إيجابيًا لأدوات أو وكلاء الذكاء الاصطناعي على الإنتاجية.

هذا يعني أن السوق لا يحتاج وكيلًا أكثر جرأة فقط؛ يحتاج نظامًا يجعل النتيجة قابلة للفحص والاستعادة ويقلل وقت التحقق البشري.

توصي الممارسات الحديثة للوكلاء بدمج التقييم البرمجي، وتقييم النماذج، والمراجعة البشرية، ومراقبة الإنتاج؛ فلا توجد طبقة تقييم واحدة تكشف جميع الأعطال. كما أن الإجراءات الحساسة أو غير القابلة للعكس يجب أن تبقى تحت موافقة بشرية.

## المستخدم الأول المقترح

### الفئة الأساسية

فرق تطوير ومنتجات رقمية صغيرة من 2 إلى 30 شخصًا:

- لا تملك فريق منصة أو SRE كبيرًا.
- تستخدم GitHub وCI وسجلات تشغيل ومتصفحًا وأدوات SaaS متفرقة.
- تتكرر لديها أعطال البناء والنشر والإنتاج.
- تريد الاستفادة من الوكلاء، لكنها لا تثق بالتنفيذ غير الموثق.

### المشتري الأول

- مؤسس تقني.
- قائد هندسي.
- وكالة تطوير تدير عدة مشاريع.
- مطور مستقل مسؤول عن الإنتاج.

### ما لا نستهدفه أولًا

- المؤسسات الضخمة التي تحتاج مشروع تكامل بيانات طويلًا.
- العمليات المالية أو الطبية أو القانونية عالية المخاطر.
- الأتمتة العامة للمبيعات والتسويق وخدمة العملاء.
- المستخدم غير التقني الذي يريد روبوت محادثة عامًا.

## سيناريوهات الاستخدام النموذجية

### 1. عطل بعد إصدار

يجمع النظام التغيير والسجلات والاختبارات، يبني فرضيات متنافسة، يعيد إنتاج العطل، يطبق إصلاحًا في فرع أو Sandbox، ثم يثبت النتيجة باختبار قبول.

### 2. فشل CI متكرر

يصنف الفشل إلى خلل حقيقي أو تذبذب أو مشكلة بيئة، يقارن بتاريخ التشغيل، ويقترح إصلاحًا مع دليل بدل إعادة التشغيل العشوائي.

### 3. بطء أو تدهور أداء

يحفظ خط أساس، يحدد التغيير المرتبط، يجرب حلولًا صغيرة، ويقارن القياسات قبل وبعد. لا يقبل عبارة «يبدو أسرع» كإثبات.

### 4. مهمة تطوير غامضة

يحوّل الهدف إلى عقد نتيجة يتضمن معيار قبول وحدودًا ومخاطر، ثم ينفذ أقل تغيير يحقق النتيجة.

### 5. مشكلة تكررت سابقًا

يسترجع حالة مشابهة مع شروط نجاحها وفشلها، ويتأكد أن السياق الحالي مطابق قبل إعادة استخدام الحل.

| Relevance AI | فرق متعددة الوكلاء دون كود | يركز على بناء قوة عاملة من الوكلاء؛ التمايز ليس إثبات النتيجة أو استرجاع الحالة |

| Braintrust وLangSmith | تتبع وتقييم الوكلاء واكتشاف تراجع الجودة | أدوات لمن يبني وكيلًا؛ ليست منتجًا يستخدمه الفريق لحل مشكلته اليومية |

## الاستنتاج التنافسي

الأفكار التالية أصبحت سلعًا متاحة ولا تكفي للتميز:

- محادثة مع ملفات الشركة.
- بناء وكلاء بلا كود.
- تعدد الوكلاء.
- ربط عشرات التطبيقات.
- خريطة معرفة للمؤسسة.
- موافقة بشرية عامة قبل الأفعال.

المساحة التي ما زالت قابلة للبناء لفريق صغير هي:

1. البدء من «حالة مشكلة» بدل Prompt أو Workflow.
2. فرض معيار نجاح قابل للتشغيل قبل التنفيذ.
3. جعل الحلول تتنافس على نفس Sandbox ونفس الاختبار.
4. تسجيل الأثر الفعلي قبل وبعد.
5. تعلّم شروط نجاح الحل، لا حفظ ملخص نصي فقط.
6. تحويل الحل إلى Playbook بعد نجاح موثق ومتكرر، لا بعد نجاح ظاهري واحد.

## تعريف المنتج المقترح

### الوعد

**أعطِ بُرهان مشكلة تقنية؛ يعُد إليك بسبب مدعوم بالأدلة، وحل مجرّب، واختبار يثبت النتيجة، وخطة تراجع.**

### المكونات الجوهرية

1. **غرفة المشكلة**
   - هدف واضح.
   - الأنظمة والملفات المشمولة.
   - القيود والإجراءات المحظورة.
   - معيار القبول.

2. **جامع الأدلة**
   - Git والتغييرات.
   - CI.
   - السجلات والمراقبة.
   - المتصفح.
   - أوامر تشخيص قراءة فقط.

3. **منافسة الفرضيات**
   - فرضيتان أو ثلاث مستقلة.
   - دليل يؤيد وينفي كل فرضية.
   - تكلفة اختبار كل فرضية.

4. **مختبر التنفيذ**
   - Worktree أو Container معزول.
   - ميزانية زمن وأدوات.
   - منع الأسرار والإجراءات المدمرة.

5. **عقد النتيجة**
   - حالة قبل التنفيذ.
   - تغيير مقترح.
   - اختبار قبول.
   - نتيجة قابلة للتكرار.
   - أثر جانبي وخطة تراجع.

6. **المراجع المستقل**
   - لا يشارك المنفذ افتراضاته.
   - يعيد تشغيل الاختبار.
   - يفحص النطاق والأمن.
   - يرفض الادعاء غير المدعوم.

7. **ذاكرة النتائج**
   - المشكلة وسياقها.
   - الحلول التي فشلت ولماذا.
   - الحل الناجح وشروط نجاحه.
   - الزمن والتكلفة والأثر.

## حدود MVP

### يجب بناؤه

- تطبيق سطح مكتب Local-first مع لوحة ويب محلية.
- ربط مجلد محلي ومستودع GitHub وGitHub Actions.
- طرفية مقيدة وأوامر قراءة فقط افتراضيًا.
- متصفح للاختبار والتحقق.
- غرفة مشكلة واحدة في كل تشغيل.
- فرضيات متنافسة.
- Worktree أو Container معزول.
- اختبارات قبول يحددها النظام ويوافق عليها المستخدم.
- موافقة صريحة قبل الكتابة أو النشر.
- تقرير أدلة قبل/بعد.
- حفظ Playbook محلي قابل للتصدير.

### لا يُبنى في MVP

- مراقبة جميع أعمال الشركة بصورة دائمة.
- بريد وSlack وتقويم وCRM.
- تنفيذ مالي أو شراء أو نشر تلقائي.
- تدريب نموذج لغوي.
- سوق للوكلاء.
- عشرات أنواع المستخدمين.
- Process Mining مؤسسي كامل.
- وعود بحل أي نوع من المشكلات.

## نموذج تقني أولي

- واجهة سطح مكتب: Tauri أو Electron، بعد مقارنة الأمان وحجم الحزمة.
- محرك محلي: TypeScript أو Rust للأذونات والعمليات الحساسة.
- Orchestrator قابل لتبديل النموذج.
- Postgres أو SQLite محلي لسجل الحالات؛ يبدأ بـSQLite.
- Git worktrees وContainers للعزل.
- موصل GitHub اختياري بصلاحيات دنيا.
- سجل أحداث Append-only مع إخفاء الأسرار.
- Policy Engine حتمي خارج النموذج.
- Verification adapters للاختبارات وHTTP والمتصفح وCI.

## نموذج العمل المقترح

- فردي محلي: مجاني أو شراء مرة واحدة بقدرات محدودة.
- احترافي: اشتراك للفرد مع نماذج سحابية وتاريخ أطول.
- فريق صغير: مساحات مشتركة وPlaybooks وموافقات وسياسات.
- لاحقًا: نشر خاص أو Self-hosted للفرق الحساسة.

التسعير لا يُحدد قبل قياس تكلفة تشغيل حالة حقيقية والوقت الذي يوفره المنتج.

## مؤشرات نجاح الاختبار الأول

خلال تجربة مغلقة مع 10 فرق صغيرة:

- حل 60% على الأقل من الحالات المختارة دون توسيع نطاق غير مصرح.
- كل ادعاء نجاح مرتبط باختبار أو قياس قابل لإعادة التشغيل.
- خفض الوقت الوسيط من فتح المشكلة إلى تحديد السبب بنسبة 30%.
- عدم تنفيذ أي إجراء عالي المخاطر دون موافقة.
- قدرة مستخدم آخر على إعادة تشغيل Playbook ناجح دون شرح شفهي.
- نسبة رفض المستخدم للتقارير بسبب نقص الدليل أقل من 20%.

هذه أهداف فرضيات تجريبية وليست وعودًا تسويقية.

## المخاطر والتخفيف

| الخطر | التخفيف |
|---|---|
| المنتج واسع جدًا | حصر MVP في مشكلات البرمجيات والأنظمة الرقمية |
| ادعاء نجاح كاذب | عقد نتيجة واختبار مستقل إلزاميان |
| تسريب أسرار | Local-first، إخفاء الأسرار، وصلاحيات أقل ما يمكن |
| تنفيذ مدمر | قراءة فقط افتراضيًا، موافقة، Sandbox وخطة تراجع |
| تكلفة نماذج مرتفعة | توجيه نماذج حسب المهمة، حدود تشغيل، وتخزين نتائج الأدلة |
| تعدد الوكلاء يزيد الضوضاء | حد أقصى لفرضيات مستقلة ومراجع واحد؛ لا وكلاء بلا دور قابل للقياس |
| منافسة المنصات الكبرى | التركيز على الفرق الصغيرة، التشغيل المحلي، وإثبات النتيجة |
| الاسم مستخدم أو متشابه | اعتماد «بُرهان» كاسم عمل فقط وإجراء فحص علامة ونطاق قبل الهوية |

## التوصية

المشروع يستحق الانتقال إلى نمذجة التدفق، بشرط تثبيت هذه الحدود:

1. المنتج الأول للفرق التقنية الصغيرة فقط.
2. نقطة البيع هي «حل مُثبت» لا «وكيل أذكى».
3. التشغيل Local-first والقراءة فقط افتراضيًا.
4. لا تُحفظ معرفة كـPlaybook إلا بعد تحقق قابل للتكرار.
5. لا نبني منصة وكلاء عامة أو بديلًا لـJira وGlean وn8n.

## الخطوة التالية بعد الموافقة

تصميم تدفق واحد كامل:

**إدخال مشكلة فشل نشر → جمع الأدلة → اعتماد عقد النتيجة → منافسة فرضيتين → تجربة معزولة → مراجعة مستقلة → موافقة المستخدم → تسليم الحل وPlaybook.**

بعد اعتماد التدفق، تُكتب وثيقة PRD النهائية ثم يُبنى نموذج تفاعلي لسطح المكتب ولوحة الأدلة.
